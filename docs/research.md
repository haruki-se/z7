# 研究用メモ

## 今回のプロトタイプの位置づけ

研究の目的は「演奏の表情をどのような物理的な動きに変換すると、人が表情・感情を読み取れるか」を比較することです。本実装は特徴抽出、動作生成、記録を担います。「楽しい」「悲しい」などの感情分類器を学習・評価したものではありません。

車体未定の段階では仮想車体で操作・対応ルールを検証します。シミュレーターの速度・加速度・旋回半径は実車をモデル化した値ではなく、評価結果をそのまま実車での印象に置き換えることはできません。

## 信号の流れ

```text
G3 / 合成デモ → Web Audio
                ├→ 出力ゲイン → PCのスピーカー
                ├→ 録音（ステレオ、最大10秒）
                └→ 解析チャンネル → AudioWorklet
                    → RMS / アタック / 発音間隔 / FFT
                    → 動作ルール → シミュレーター
                                  → 実験ログ
                                  → 任意：HTTP → Python → UDP → 受信機
```

Pythonの音声ライブラリを必須にする代わりに、既存アプリのブラウザ音声入力を拡張しています。通常起動に追加パッケージが不要で、同じ画面で入力・解析・比較・保存を行えます。将来、ASIO固有の制御や厳密なリアルタイム制御が必要なら、Python/ネイティブの音声入力と比較して置き換えを検討します。

## 解析

AudioWorkletで2,048サンプル窓・1,024サンプルホップ。サンプルレートはAudioContextの実際の値を使います。44.1 kHzでは約46.4 msの窓・23.2 msのホップです。画面、指令生成、ログは50 ms周期を目標に更新します。実際の更新間隔はログの`elapsed_ms`で評価してください。

- **RMS**：`sqrt(mean(x²))`。dBFSは`20 log10(RMS)`、数値上の下限は−120 dBFS。
- **ピーク**：窓内の最大絶対値。0.98以上をクリッピング付近として表示。
- **アタック**：ゲートを超え、平滑化dB値との差が設定値以上、前窓から3 dB以上上昇、前のアタックから180 ms以上。閾値ベースの簡易検出で、ピッキングの真値ではありません。
- **BPM**：4回以上のアタックから最大8発音間隔の中央値を取得。40〜240 BPMに対応する間隔で、中央値絶対偏差 / 中央値が0.2未満のとき表示。2秒以上発音がないと失効。
- **安定度**：上記の偏差から算出する間隔の規則性。統計的に校正された正解確率ではありません。
- **スペクトル重心**：Hann窓FFTの片側振幅スペクトルで、DCを除いた `Σ(frequency × magnitude) / Σ(magnitude)`。音の明るさの目安。基本周波数や音名を返すものではありません。

持続音からテンポは求まりません。奏法、和音、ミュート、ノイズ、エフェクトによってアタックの誤検出、倍・半テンポが起きます。これらの精度は実録音のラベルと比較して評価する必要があります。

## 動作ルール

`intensity = clamp((db - gateDb) / (fullDb - gateDb), 0, 1)`

- **A：強弱のみ**：前進目標値 = `intensity × maxSpeed`、旋回は0。
- **B：表情を含む**：安定したBPMがある場合、前進目標値に`clamp(BPM / 120, 0.6, 1.4)`を乗じ、`maxSpeed`以下に制限。新しいアタックごとに旋回方向を左右交互にし、旋回量を`maxTurn × intensity × exp(-アタックからの秒数 / 0.25)`とします。
- 前進の追従は時定数による一次平滑化。無音と更新途絶では平滑化を待たず0にします。
- 左右車輪指令は`speed + turn`、`speed - turn`を最大絶対値1以内へ同じ比率で正規化。正の旋回指令を画面上の時計回りとして描画します。

上限はGUIで0〜0.6に制限します。実車に適用する場合は車輪半径、トレッド幅、ドライバーの不感帯、左右差、加減速を校正し、受信側でも別途上限を設けます。

## 停止条件

- 入力のRMSが無音判定以下：生成指令を0。
- 新しい解析結果が250 ms以上来ない／音声時刻が250 ms以上古い／AudioContext停止：生成指令を0、UDP送信を解除。
- 全停止、Esc、画面非表示：動作を一時停止し、スピーカー出力・UDP送信をオフ。
- 入力停止・切断：解析・録音・実験記録・UDP送信を終了。
- 対応ルール・解析チャンネル・パラメーター変更：UDP送信を解除。
- ブリッジへの指令更新が350 ms途絶える、またはACKが500 ms途絶える：ブリッジ停止・セッション失効。
- 受信機への有効な指令更新が350 ms途絶える：受信機停止。新しいセッションのゼロ指令から再開。

ブラウザとOSにはスケジューリング遅延があり、ハードリアルタイムの保証はありません。実車では物理停止手段と受信側の停止処理が必要です。

## 実験例

1. ルールA/Bそれぞれで同じ8小節を演奏。入力感度、上限、G3の音色を統一。
2. 実験メモに条件、被験者の匿名ID、テイク番号を記載。ルールの順序を交互にするなど順序効果を抑える。
3. 音声録音とログを保存。JSONには音源区分が入るので、合成音の結果と実演奏を混在させない。
4. 応答遅延・無音での停止・誤アタック・指令のばらつきを定量評価。
5. 動画や実車を観察して「演奏との一致」「躍動感」「意図の読み取りやすさ」などを質問し、条件間で比較。

実験ログには観察者の回答や実車センサー値は自動で含まれません。これらは別途収集して、同じ実験IDで対応づけます。
